Profiling and repeatable workload

Development builds retain 120 frame samples per phase. The diagnostics overlay reports average, nearest-rank p95, and worst frame time; performance in the F2 console prints the same summaries with update, draw, and present phase averages. Timed phases are frame, event processing, asset watcher polling, fixed update, audio maintenance, world draw/submission, and presentation. Asset reload work performed inside the game’s update remains part of update timing.

Run the deterministic rendering workload with:

zig build run-benchmark

It updates 10,000 simple moving game entities, rebuilds a collision grid for their moving colliders, performs 1,000 region queries per fixed update, and draws one tinted sprite per entity from one 4x4 texture at a 320x180 native view. Entities start in a fixed 100-by-100 grid and wrap horizontally; the workload and texture are the same each run and use no random state or dynamic spawning. Use the same build mode, resolution, vsync setting, and graphics backend when comparing results. Let it run past its 60-frame warm-up and the 120 frames it summarizes, then record average, p95, and worst frame times along with the individual phase averages. F3 toggles the overlay; F2 opens the console, where performance prints the current summary; Escape quits.

Run the typography reference workload with:

zig build run-text-benchmark

It draws the authored bitmap font, BFNT coverage, runtime-shaped Latin and Tamil, and MSDF from the same native 320x180 view. Use F10 to compare SDL_GPU with SDL3 2D; Escape quits. After its 60-frame warm-up and 120-frame sample window, it logs frame average/p95, shaping and measure time, cache hits and misses, rasterized glyphs, atlas pages and CPU bytes, upload regions/bytes, and draw calls. The timings are local to the loaded font workload. Capture screenshots on a display for visual review; the log is profiling evidence, not screenshot acceptance.

At shutdown, the engine also reports cumulative shaping, cache, atlas upload, and retirement counts. Those counters are useful for diagnosing a run but are not a machine-independent performance baseline. For cold/warm comparisons, use the reference workload and record its machine and backend details as above.

The measurements are deliberately runtime-local and are not uploaded. No machine-independent baseline is committed because results depend on hardware, drivers, window compositor, and vsync. Record the machine/OS, CPU/GPU, Zig version, build mode, backend, and workload count beside any captured measurements. The overlay’s counters include sprites/draw submissions, the game’s published entity count, texture-cache counts/estimated bytes, and gameplay-published collision query calls.

-Dtracy=true additionally enables Tracy zones for function-level investigation. Compare the repeatable workload first and use those zones to locate a measured bottleneck before changing data layouts or caches.

The benchmark also logs that summary itself, under the benchmark log scope, once the warm-up and 120 frames are recorded. It reports cumulative collision query calls and hits as well. The benchmark turns on Config.gpu_timing, so it logs the GPU summary too, and it logs the spike count with it. Its frame figures therefore include the GPU wait. It runs only in development builds, where the frame times are kept, so a release build logs nothing.

The overlay shows a strip of allocations per frame and a line of per-frame plot values. The plots are sprites queued, draw calls made last frame, allocations requested so far this frame across every scope, and bytes requested. Each plot keeps the same 120-frame window as the frame graph, so its average and p95 are over those frames. Allocation counts restart at the start of each frame, while the totals in the memory line keep counting from startup.

-Dtracy=true also sends those four plots to Tracy, and it draws them beside the zones. The plot calls use Tracy’s C entry point ___tracy_emit_plot. If a Tracy build fails to link on that name, check the Tracy headers in the vendored tree.

GPU time is measured only when Config.gpu_timing is set, and the benchmark sets it. The engine then submits each frame and waits on a fence until the GPU finishes it. That wait is the gpu phase, it is the last part of present, and it is sent to Tracy as the gpu ms plot. The pass zones still measure only the CPU’s recording work. SDL’s GPU API, as this engine uses it, does not appear to expose timestamp queries, so the figure covers the whole frame and not each pass. Confirm this against the pinned SDL version before relying on it.

The wait stalls the CPU, so with gpu_timing on the CPU and GPU work add up. Those frame times measure a cost, not a rate to play at, and they should not be compared with a run that leaves the option off.

A frame longer than two 60 Hz budgets (33 ms) is a spike. The overlay shows how many have happened since startup, and the latest one with its frame count and the phase that took most of that frame. Spikes are recorded only in development builds.
